# Account deletion deployment

Target project: `qaxeirbqyrmakwuwvpto`. Do not deploy to a substitute project.

Deployment completed on 2026-10-21 in the intended project through its verified Supabase pooler connection. Preflight found only `routines` and `routine_exercises` missing among the required owned tables. The lead applied `supabase/migrations/202610210000_routine_prerequisite.sql` followed by `supabase/migrations/202610210001_account_deletion.sql` in one transaction and committed both. The prerequisite creates only those two canonical tables, indexes, grants and owner policies. The full historical schema was not rerun. No service role key belongs in the app. The UI enables deletion only when the authenticated capability RPC returns version 1 from the configured backend.

For a deployment or repeat verification, check these behaviors with disposable fixture accounts. The live SQL verification below covers the database checks; native device checks remain separate:

1. Seed every owned table, plus public foods and another account's data. Keep row counts by owner.
2. Check capability returns 1 as authenticated. Verify anonymous and unauthenticated callers cannot delete, even when passing forged owner identifiers (the function accepts none).
3. Delete A. Verify its auth user, sessions, food logs, foods, weight entries, meals, goals, profile, workouts, exercises, routines, device claims and merge tickets are gone. B and public foods must remain.
4. Force a deletion failure with a transaction-local trigger and verify all rows and auth user roll back. Remove the trigger.
5. With A's original valid JWT, verify `account_deletion_status()` returns true after a lost response. Verify repeat `delete_own_account()` calls reject the missing identity, all owned-table reads/writes are denied, and B cannot see A's receipt. Verify in-flight writes and deletion serialize through the auth-row locks.
6. On device, verify offline failure retains local data, duplicate taps send one request, a restore or sync cannot race deletion, confirmed deletion clears local data, and interrupted local cleanup resumes before a new anonymous session starts.
7. Verify exported Apple Health samples remain and the confirmation explains that fact.

The migration deliberately fails atomically if a required table is absent. If future owned tables are added, extend this RPC and these checks in the same release. Database deployment and rollback-only SQL verification are complete for the configured target. Native permission, sign-in and interrupted-cleanup checks still require a device.

The completion receipt stores only the deleted account UUID and completion timestamp, with no direct client table access. Only the JWT owner can query its boolean completion status. Receipts are retained to distinguish a lost success response from an unavailable backend; privacy documentation must include this limited recovery record. Deleting the receipt ends recovery for that request.

Disposable SQL verification: execute `supabase/tests/delete-own-account-bootstrap.sql`, the migration, then `supabase/tests/delete-own-account.sql` in a fresh PostgreSQL or PGlite database. Bootstrap creates mocked auth functions and minimal owned tables and must never run in a real Supabase project. The regression SQL rolls back its fixtures. It covers ownership, shared rows, auth/merge cleanup, privileges, injected rollback and surviving JWT read/write denial.

The migration is additive. Rollback requires replacing the application capability and deletion functions first; removing live-account policies would reopen stale-token writes and should not be used as a rollback. Deleted account data cannot be recovered by rolling back the schema.

Pending deletion recovery remains visible independently of current auth status and capability. A confirmed local phase can finish cleanup after session expiry. An unconfirmed phase never treats an expired token, missing session or RPC error as deletion success. It offers server verification retry plus an independently confirmed device-only removal action whose warning states that the cloud account and data may remain. Device-only removal makes no cloud deletion claim.

Live verification on 2026-10-21: `supabase/tests/delete-own-account-live.sql` passed against the intended project, using its real NOT NULL columns and auth foreign keys. It inserts random disposable A/B/anonymous users, auth sessions and identities, all 13 owned datasets, device claims, both merge-ticket references and a shared fixture food inside a single rollback-only transaction. The fixture metadata explicitly uses JSONB casts for the real auth schema. The test verified injected failure rolls back every owned table, authenticated deletion removes only fixture A and its auth sessions/identities, fixture B and shared food remain, anonymous and unauthenticated deletion are denied, deleted-identity claims cannot write, repeated destructive calls reject the missing user, and recovery receipt visibility is restricted. The final ROLLBACK residue check passed. Execution log: `/private/tmp/issue99-live-regression.log`.

The live SQL test sets transaction-local JWT claims and database roles to exercise the real RPC and RLS contracts. It does not replace a native sign-in/deletion flow. The separate real-token HTTP and two-connection checks described below cover issued-token and lock-serialization behavior. No real user accounts were deleted or changed by the regression. Test-trigger creation and all random fixtures were rolled back.

For future deployment, first preflight required tables and constraints read-only. Run the bounded routine prerequisite only when deploying this documented schema gap, then the deletion migration in the same caller-owned transaction. Commit only when both succeed. Run the live fixture SQL separately with `psql -X -v ON_ERROR_STOP=1 -f supabase/tests/delete-own-account-live.sql` through the verified target connection. An error must close or roll back that connection; never commit the fixture transaction. The script sets short lock and statement timeouts to bound interference and never targets existing account IDs.

Real-token HTTP verification on 2026-10-21: `python3 supabase/tests/delete-own-account-http.py` passed against the same intended project. The script creates a random, marked GoTrue anonymous fixture, verifies its actual token cannot delete, converts only that fixture to an email identity, refreshes through GoTrue for a real nonanonymous token, verifies capability 1, and calls the deletion RPC over HTTP. The fixture auth user and owned goals were removed, the surviving issued token could query its recovery receipt, and its owned-row INSERT was denied with HTTP 403 / SQLSTATE 42501. A bounded two-connection identity-lock check also passed. Cleanup removed the exact fixture and its receipt. Log: `/private/tmp/issue99-http-smoke.log`. Tokens, passwords and keys are never printed by the script.

Two-connection verification on 2026-10-21: `python3 supabase/tests/delete-own-account-concurrency.py` passed both lock directions against the deployed RLS and RPC. First, an authenticated owned-goals UPDATE held the live-account KEY SHARE lock until COMMIT; deletion waited and then removed the committed row. Second, deletion held the auth-row FOR UPDATE lock before COMMIT; a concurrent new owned-food INSERT waited, then failed with SQLSTATE 42501 after identity deletion committed. Statement/lock/process timeouts bound both checks. Both exact random fixture accounts, owned rows and receipts were cleaned up. Log: `/private/tmp/issue99-deletion-concurrency.log`.

Both repeatable Python scripts read the existing `.env` from the repository root and validate the exact intended Supabase URL before making requests. They use `psql` and Python standard-library modules without repository dependencies or embedded credentials. Their fixture names use the `issue99` prefix and random identifiers. Run only with explicit disposable-fixture authorization and never adapt them to target an existing user. Native device sign-in, permission sheets and interrupted app cleanup remain manual acceptance checks.
